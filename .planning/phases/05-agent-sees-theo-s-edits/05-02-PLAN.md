Python matrix (CLAUDE.md): the unit tests run on 3.11 and on 3.14 under `./scripts/check.sh`. `theo_edit.py` runs under the gateway venv Python, because it imports the Hermes storage and session reader through the plugin. `delta_live.py` imports only the standard library and runs under `.venv-py3.14/bin/python -I`, as `tests/live/own_job/analyze.py` does (the system python3 links SQLite 3.40.1).

SC3 reading (record it in the SUMMARY): the roadmap line and the CONTEXT discretion line compare turn 30 with a session that has no plugin. Plan 05-07 measures that arm. It also keeps the edits arm against the no-edits arm, so the report holds three measured numbers: the notes size, the plugin fixed cost, and the sum against the no-plugin arm. The SUMMARY of 05-07 puts the measured fixed cost next to the one derived from the code.

Mechanism for the no-plugin arm (record it in the SUMMARY; this differs from the plan checker's example route on purpose):
1. All three arms run in twin test homes built by `make_home.py` from the same allowlisted copy of the real config.yaml. Home A has the plugin on, home B has it off. A real-home plugin arm against a test-home bare arm would differ by more than the plugin: the MCP servers and their tokens, the memory provider prefetch, the skills and SOUL.md. Twin homes make quiet minus bare the plugin alone.
2. No secret file at all (house rule 15). The model provider is the plugin `claude-subscription-directsdk-experimental`. It runs the Claude Code CLI with the credentials of the Claude Code store, outside HERMES_HOME (`directsdk_setup.py` `apply_config_dir`: the plugin setting, else `CLAUDE_CONFIG_DIR`, else the CLI default), so a test home needs no key. make_home never links, copies or reads `.env`, `auth.json` or `mcp-tokens`, and it has no option to do so. The source config.yaml is parsed in memory only to take the allowlisted sections; the `mcp_servers` and `secrets` sections are never written or printed. If the probe in plan 05-07 gets an auth error, that task stops and tells Theo in one plain line; no secret and no Infisical step is added.
3. A headless `hermes chat` under a test HERMES_HOME starts its own idle-exit gateway for that home (`hermes_cli/gateway_client.py` `connect_gateway` calls `ensure_gateway_runtime(home, idle_exit=True)`). The test homes live outside `~/.hermes/profiles`, so the real multiplexer does not serve them (`hermes_cli/gateway_runtime_multiplex.py` `multiplexer_root_for`). `arms` stops each test gateway itself when the runs end.
4. Listeners and pollers (round 2 checker warning). The real gateway listens on 0.0.0.0:8644 (the webhook platform) and on one loopback runtime port (`ss -ltnp`, 2026-11-02). Hermes listener settings are platform blocks (`webhook` with WEBHOOK_PORT default 8644, `api_server` with API_SERVER_PORT default 8642, `msgraph_webhook`), `proxy.tunnel_port` and the managed model server `port` (`hermes_cli/config_defaults.py`). make_home writes every platform block and `proxy` disabled, and it turns off the passive update checks, which call outside services. The kept sections of the real config hold no port, listen or bind key (scanned 2026-11-02); a future one stops the build. The 05-07 probe then compares the test gateway's ports with the real gateway's.

Why the optional reminder split exists now (record it in the SUMMARY): D-36 names its own fallback (the one reminder line comes back), and RESEARCH predicts the own-plan gate in plan 05-05 will need it. With the split built and tested here, plan 05-07 runs the token arms on whatever plan 05-06 settles, with no tool change in a live plan.
